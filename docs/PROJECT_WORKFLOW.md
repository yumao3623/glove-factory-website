# 长期项目执行与交接规则

用户授权来源：2026-09-22 项目治理指令。适用于开发、修复、SEO/GSC、内容、账号、支付、部署和基础设施任务。不依赖单个聊天记忆。

## 每次开始

1. 先按根目录 `AGENTS.md` 的顺序读取 `PROJECT_STATUS.md` → `HANDOFF.md` → `ROADMAP.md` → `PROJECT_WORKFLOW.md`；需要历史才读 RELEASE_HISTORY.md 和相关原始验收。不要默认重读几十份历史报告。
2. 检查 cwd、git status、当前分支、远端 main 与既有未提交工作；确认本次 Product / Growth / Operations / 外部等待类别与有范围目标。
3. 当前事实优先于旧计划；记录证据日期及“本次实查 / 历史验收 / 用户报告 / 未验证”。平台权限不足不等于服务故障，不删除已有资源重建。
4. 未选择并满足进入条件前 Development=无；新聊天、核查、等待和文档整理不产生 release。

## 版本及发布

- 历史 1.x、2.0、2.1、2.1.5、2.2 不更名。当前产品状态按已验证部署表达；本次 2.3.0 已完成，因此当前稳定生产版本为 Production 2.3.0。后续仅在新的代码能力达到 DoD 时创建下一版本。
- PATCH：有范围的小 bug/文案/样式/接口/SEO 代码修复；MINOR：完整新能力；MAJOR：产品定位/核心架构/商业模式/整体体验显著变化。
- 单纯内容录入、GSC/外链、服务检查、账号操作一般不变版本；是否需要开发按实际变化判断。
- 新代码分支默认 codex/，尽量一次任务一个清晰范围。不要重写旧提交/删除历史分支或 tag 美化记录。
- production version 只在对应生产部署与验收可证实时更新；pending merge / main pushed / build ready / alias live / E2E verified 分别记录。
- 真正发布时同步 package.json、lock 根包版本、release 记录、commit SHA、部署 ID/URL；不要将包版本当部署证明。
- 不假造历史 Git tags；若创建未来 release tag，必须指向已验收代码并记录证据。

## 结束前维护仓库

- 更新 PROJECT_STATUS 的变化、证据时间和限制；若无变化只更新必要核查信息，不复制流水账。
- HANDOFF 保持短：最近完成、当前等待、触发条件、唯一下一任务。详细 release 验收在专门记录中，不塞入 handoff。
- ROADMAP 仅保留 2–4 个有价值候选；进入/取消/调整顺序必须有业务理由，不受旧任务编号强迫。
- RELEASE_HISTORY 只在真实交付发生时追加简短记录。
- 按改动做相关检查。纯文档检查链接、冲突、diff；不为此跑完整生产写入测试、发邮件或部署。
- 如本地提交未推送，必须明确指出，避免下一台机器误用旧规则。main 更新会触发 Vercel 时记录影响；不混入未知用户改动。

## 每次固定结束报告（不可省略）

1. **当前版本**：Production；Development（无则写无）；Current work（含是否只是运营，不加版本）。
2. **本次实际完成**：分别写代码/文档修改、检查/测试、Git commit、main push、Vercel 部署、生产验证、第三方实际操作；准备但未执行单独标明。未做的不可报完成。
3. **真实状态**：Product / SEO / Search Console / Multilingual / RFQ & Email / Payment / Deployment & Infrastructure，各用一句说明重要变化及证据边界。
4. **未完成四类**：可以现在继续做 / 外部等待 / 真正阻塞（注明只阻塞哪件事）/ 暂时不值得做。
5. **下一步**：明确当前版本是否完成、当前阶段、是否开启下一版本、推荐目标和启动条件；只有等待时说“现在没有必要改代码”，给下次检查日期或事件。
6. **对话建议二选一**：“继续当前对话”或“新建 Codex 对话”，说明原因。继续则给“下一条直接发送”；新建则给可复制“下一条 Codex 提示词”，包含仓库路径、状态入口、本次边界及固定报告要求。不能让用户重讲版本史。

## 触发式维护

- Google：先按 ROADMAP 日期检查；有效 query/page/impression 数据出现后再决定内容优化，首次索引不自动开版本。
- RFQ：真实反馈、保存/投递失败或超出约定响应目标时跟进；先看后台和邮件证据，不自动重建工作流。
- 内容：新增批准产品/新工厂证据触发资料更新与必要页面评审。
- 支付：企业条件与付款需求同时齐备才启动交付；没有条件不反复改适配器。
- Operations：监控异常/服务告警/权限或域名变化立即处理，不等待 SEO；正常运行不为活跃而重构。
- 本规则是人工任务触发机制，不代表已经创建自动监控、定时任务或通知服务。需要自动化时另建有明确频率和通知条件的任务。

## 历史文档地位

V1 roadmap、旧 infrastructure、commerce 基础和早期 ADR 是历史证据，不再控制当前执行顺序。旧证据、产品来源许可、IP 隔离、未知商业事实不得因此被抹掉。当前用户明确授权整理治理，取代旧“每个检查点都先 Human Review”的通用流程；真实商业事实批准、对外发送、付款和安全权限仍依实际授权处理。
